# D8.3 — Multi-Lease Adversarial Validation

## Objective

Validate the D8.1 Global Budget Broker and D8.2 Execution Binding adapter against adversarial conditions at the Gateway / shared-Broker boundary. This stage adds integration-level attack tests rather than duplicating the standalone Broker's existing quota, replay, crash, and independent-process tests.

## Newly covered attacks

1. **Global operation-ID collision across Leases:** two distinct Gateways race the same operation ID under different signed Leases. Exactly one operation may consume the global sequence and produce a tool effect; the second binding must fail closed.
2. **Lease-local exhaustion:** exhausting one Lease must not block another active Lease, while neither Lease may exceed its own reservation.
3. **Receipt metadata persistence:** the signed Gateway receipt's global budget ID, Lease Grant digest, global sequence and per-Lease usage count must remain in the durable Execution Journal and survive Gateway reconstruction.
4. **Crash, revocation and expiry during recovery:** crash after the Broker has durably committed a budget operation but before the Gateway persists its budget receipt; then revoke and expire the Lease, reconstruct the Broker/adapter/Gateway, and recover only the exact already-pending/committed operation. No new budget operation is authorized for an inactive Lease.

## Protocol clarification and fixes

- The `after_budget_allocation` crash point is placed immediately after the Broker returns a validated durable receipt and before the Gateway persists `BUDGET_CONSUMED`. This makes the test exercise the actual Broker-replay recovery boundary.
- The Gateway persists global receipt metadata once, atomically with the `BUDGET_CONSUMED` transition; it must not overwrite the global fields with a legacy metadata-free update.
- An inactive/expired Lease may be used only to settle/replay an exact durable Broker operation whose operation ID, Lease ID, signed Grant digest and request digest all match a `PENDING` or `COMMITTED` ledger entry. The Broker remains the final authority and rechecks the same binding under its global lock. New operations for expired or revoked Leases remain rejected before the Gateway writes a new execution record.
- An existing inactive Lease binding may be reconstructed from its exact persisted signed Grant. This is recovery metadata only; it does not reactivate the Lease or restore its ability to consume new quota.
