# D8.0 — Multi-Lease Global Budget Protocol Design

**Repository:** `kaikai-cao/offline-agent-budget-lab`
**Branch baseline:** `experiment/tool-capability-contract`
**Baseline commit:** `d1ac1d92db688d89ce9cc046f9e032befbec9b3a`
**Status:** D8.0 design approved; D8.1 standalone implementation prepared
**Target implementation:** new sibling package `e4_8_4_multi_lease_budget/`

## 1. Objective

E4.8.2 currently models one `DurableCounterBroker` bound to one `lease_id` and one `quota_limit`. E4.8.3 binds one execution to that broker. The next research question is how multiple independently authorized Leases can share one finite global budget without exceeding either the global ceiling or their own quotas.

D8.0 defines the protocol and acceptance criteria. It does not modify E4.8.2/E4.8.3 or perform real TPM operations.

## 2. Chosen model: reserve quota per Lease, consume from one global counter

Let:

- `G` = immutable global budget limit for one budget epoch;
- `Q_i` = quota reserved for Lease `i`;
- `U_i` = budget units consumed by Lease `i`;
- `A` = total quota reserved across all registered Leases;
- `S` = total consumed budget units across all Leases;
- `C0` = counter value recorded when the epoch is initialized;
- `C` = currently observed counter value.

Required invariants:

```text
A = Σ Q_i                    and A <= G
0 <= U_i <= Q_i              for every registered Lease i
S = Σ U_i                    and S = C - C0
0 <= S <= A <= G
```

One accepted budget-consuming operation causes exactly one global counter increment. The operation consumes one unit from its own Lease and one unit from the global pool. The global counter value is the unique sequence number across all Leases.

Quota is reserved when a Lease is registered, not only when its first operation executes. This prevents independently issued offline Lease grants from collectively promising more than the global budget.

### Conservative reservation policy for the first implementation

A Lease reservation is immutable and is not refunded when the Lease expires or is revoked. Unused quota is therefore unavailable to later Leases in the same epoch. This deliberately favors safety and a simple proof of the global bound over utilization. Quota reclamation requires a later protocol proving that an old Lease can no longer be used by an offline holder; it is out of scope for D8.0/D8.1.

A new budget epoch requires a new `global_budget_id` and a separately initialized journal/counter domain. Do not reset `G` or reuse an old epoch in place.

## 3. Lease authorization and registration

A Lease registration must be backed by the Issuer-signed authorization already used by E4.8.3, extended with a signed `global_budget_id`. The global-budget path uses a versioned LeaseGrant schema (proposed version 3); legacy v1/v2 grants remain valid only for the existing single-Lease path and must not be accepted by the new Global Budget Broker. The signed fields relevant to the global budget are:

- `issuer_id`, `grant_id`, `lease_id`, `nonce`;
- `global_budget_id`;
- `quota_limit`;
- `issued_at`, `expires_at`;
- the intended Gateway audience and the ordinary tool/context permissions.

The new Global Budget Broker is configured with the trusted Issuer public key and verifies the signature itself. It must not trust a caller-provided `quota_limit` or a caller assertion that a grant was already verified. The broker verifies that the grant's `global_budget_id` matches its own immutable epoch ID. `grant_digest` is computed over the canonical signed payload (excluding the signature field), using the same canonical JSON rules as E4.8.3. D8.1 must extend the LeaseGrant signed payload with `global_budget_id`; the Broker verifies the exact payload and Ed25519 signature rather than importing an untrusted Python object.

Registration runs under the same global admission lock as consumption and an SQLite `BEGIN IMMEDIATE` transaction:

1. Verify the Issuer signature and grant shape.
2. Verify budget epoch, validity interval, unique non-empty identifiers, and positive quota.
3. If `lease_id` already exists with the exact same grant digest and metadata, return the existing registration (idempotent registration).
4. If the same `lease_id`, `grant_id`, or nonce is presented with different signed content, reject it as a binding conflict.
5. For a new Lease, compute `A` from all prior reservations. Admit only when `A + Q_i <= G`.
6. Persist the immutable Lease record and its initial `used_count = 0`.

A Lease ID is allocated once per immutable Lease grant. A changed quota or replacement authorization uses a new Lease ID and a new reservation; the old reservation is not silently overwritten.

## 4. Global Broker state

The new package should own one shared journal and one shared monotonic-counter adapter for the entire budget epoch. The main records are:

### `budget_meta` / epoch metadata

- `global_budget_id`
- `global_quota_limit` (`G`)
- `baseline_counter_value` (`C0`)
- `expected_counter_value`
- `health` and `health_reason`
- pinned Issuer public-key digest and Broker configuration identity

The epoch configuration is immutable after initialization. A changed limit, Issuer key, storage path, counter path, or lock domain must fail closed.

### `leases`

- `lease_id` (primary key)
- `grant_id` and nonce (unique within the epoch)
- `grant_digest`
- `quota_limit` (`Q_i`)
- `used_count` (`U_i`)
- `issued_at`, `expires_at`
- state (`ACTIVE`, `EXPIRED`, or `REVOKED`)

`quota_limit` and `grant_digest` are immutable. `used_count` is updated only in the same transaction that commits the corresponding global counter receipt.

### `operations` and `receipts`

- globally unique `operation_id`
- `lease_id`
- `request_digest`
- pre-increment counter value
- state (`PENDING`, `NOT_APPLIED`, `COMMITTED`, `INDETERMINATE`)
- committed global sequence / counter value
- durable receipt bound to Lease ID, Operation ID, request digest, and global sequence

Operation IDs are unique across the whole epoch, not merely within a Lease. Reuse with a different Lease ID or request digest is rejected.

## 5. Consume protocol

All Lease operations share one Broker admission lock. Per-Lease locks are not sufficient because they cannot protect the global counter or global reservation invariant.

For a new operation:

1. Verify the signed Lease grant and its global budget epoch.
2. Acquire the single global cross-process Broker lock.
3. Check the operation ID first. An exact committed replay returns its original receipt without incrementing; a mismatch is rejected.
4. Recover any existing pending counter intent before admitting another operation. The first implementation permits at most one pending global counter increment.
5. Check Broker health and compare observed counter `C` with the journal's `expected_counter_value`.
6. Check Lease state and validity. New operations require an active, unexpired Lease and a matching persisted grant digest.
7. Check `U_i < Q_i` and `C - C0 < G`. Keep both checks even though `A <= G` and `U_i <= Q_i` imply the global bound; the global check is defense in depth.
8. Persist a `PENDING` intent containing `operation_id`, `lease_id`, request digest, and pre-increment counter value.
9. Increment the one global counter and read it independently. Require exactly `C + 1`.
10. In one SQLite transaction: store the receipt, mark the operation `COMMITTED`, increment that Lease's `used_count`, and advance `expected_counter_value`.
11. Return the receipt. Tool execution remains downstream, as in E4.8.3; a consumed budget unit is not refunded if the tool later fails.

A per-Lease quota exhaustion rejects only that Lease. Other active Leases may continue if the global pool and Broker health permit it.

## 6. Crash recovery

Recovery is performed under the same global lock and before any other Lease is admitted:

| Observed counter delta from pending pre-value | Recovery action | Lease accounting |
|---:|---|---|
| `0` | Mark operation `NOT_APPLIED`; do not retry the same operation ID | Do not increment `used_count` |
| `1` | Reconstruct and commit the original receipt | Increment that pending operation's Lease `used_count` exactly once |
| Any other value, negative delta, or multiple pending intents | Mark global Broker `INDETERMINATE`; stop all Lease consumption | Do not guess which Lease should be charged |

Recovery of an already-persisted pending intent is journal repair, not a new budget authorization. It may settle that intent even if the Lease has since expired or been revoked, but it must match the exact persisted Lease/grant/request binding and must not admit a new operation. This avoids stranding the global counter journal solely because the wall-clock validity interval elapsed during a crash.

This counter recovery does not recover downstream tool side effects. E4.8.3's tool lookup/idempotency and Gateway receipt recovery rules continue to apply separately.

## 7. Expiry, revocation, and offline behavior

- Expiry and revocation stop **new** operations for that Lease.
- A revoked or expired Lease does not release its reserved quota in this first model.
- A revocation is an Issuer-signed record binding `global_budget_id`, `revocation_id`, `lease_id`, the original `grant_digest`, and `revoked_at`. The Broker verifies it with the pinned Issuer key, accepts an exact replay idempotently, rejects a conflicting reuse of `revocation_id`, and makes the Lease state transition irreversible to `REVOKED`.
- A revocation is effective offline only after the Broker has received and durably stored that authenticated record. An offline Gateway cannot learn a revocation that has not reached it; the signed expiry remains the hard offline time bound.
- A pending Broker counter intent may be settled as described above, but no new budget unit may be allocated after expiry/revocation.
- Renewal uses a new Lease ID and a new reservation. No implicit in-place quota increase.

Revocation delivery, secure clock assumptions, recovery grace for external tool execution, and quota reclamation need separate threat-model decisions before production use.

## 8. Concurrency and trust boundary

Supported in D8.1:

- one host;
- cooperating Gateway/Broker processes;
- one shared journal, one shared counter state, and one global lock path;
- SQLite transactions plus the OS file-lock behavior already modeled in E4.8.2.

Not supported:

- independent hosts with local counters or separate lock domains;
- distributed consensus or a network coordinator;
- malicious local administrator/kernel, arbitrary direct counter writes, or replacement of all software trust state;
- hardware NV command transport ambiguity, TPM/TEE isolation, or direct TPM attestation.

The global Broker is the shared admission point. Every participating Gateway must use it; bypassing it invalidates the global budget guarantee. The first implementation remains a software model, not a production-grade multi-host service.

## 9. Acceptance tests for D8.1/D8.2

### Lease registration

1. Exact registration replay is idempotent.
2. Duplicate Lease ID with changed grant digest/quota is rejected.
3. Duplicate Grant ID or nonce is rejected.
4. Invalid signature, wrong global budget ID, expired grant, malformed quota, and invalid/conflicting revocation records are rejected.
5. Concurrent registrations cannot make `ΣQ_i` exceed `G`.
6. A reservation that would make `A + Q_i > G` is rejected without partial insertion.

### Consumption and replay

7. Two or more Leases consume from one global sequence with unique monotonically increasing values.
8. Each Lease is independently limited by its own `Q_i`.
9. Total consumption never exceeds `G`.
10. Exhausting one Lease does not block another Lease while global budget remains.
11. Exact replay returns the original receipt and does not increment either global count or Lease usage.
12. Reusing an Operation ID across different Leases or request digests is rejected.
13. Concurrent processes consuming through different Leases receive distinct global sequence values.

### Crash and integrity

14. Crash after intent recovers as `NOT_APPLIED` without charging the Lease.
15. Crash after increment/read commits one receipt and charges the correct Lease exactly once.
16. Crash after receipt commit replays the same receipt.
17. Multiple pending intents, out-of-band increments, anchor mismatch, or stale journal restoration fail closed globally.
18. Expiry/revocation blocks new consumption but does not prevent safe settlement of an already-persisted Broker intent.
19. Changed global epoch, global limit, Issuer key, journal/counter/lock configuration fails closed.
20. The same suite passes under independent OS processes, not only threads.

### Invariant assertions

After every test operation, assert:

```text
SUM(leases.quota_limit) <= global_quota_limit
0 <= leases.used_count <= leases.quota_limit
SUM(leases.used_count) == expected_counter_value - baseline_counter_value
observed_counter_value == expected_counter_value when health == READY and no pending intent exists
```

## 10. Implementation plan after D8.0 approval

### D8.1 — standalone Global Budget Broker

Create `e4_8_4_multi_lease_budget/` as a new sibling package. Reuse the E4.8.2 software counter/lock assumptions conceptually, but do not edit the existing E4.8.2 implementation. Add signed Lease registration, immutable quota reservations, one global operation journal, per-Lease accounting, crash recovery, and the focused broker test suite.

### D8.2 — Execution Binding integration

Add a narrow adapter between E4.8.3 Gateway and the new Broker. Remove the one-Lease constructor assumption only in the integration path. Preserve D7.1–D7.7 behavior and tests. A Gateway must pass the exact signed Lease authorization; the Broker independently verifies the Issuer signature and global budget ID.

### D8.3 — cross-Lease adversarial validation

Run thread and independent-process concurrency tests, quota-allocation race tests, per-Lease exhaustion, replay, crash recovery, revocation/expiry, and global invariant checks. Freeze the offline global-budget model only after the complete suite passes.

## 11. Explicit non-goals

D8.0–D8.3 do not implement Online coordination, cross-host consensus, quota refund/reallocation, TPM NV writes, TEE isolation, multi-Issuer federation, or production operations. Online coordination is a subsequent stage and must build on the same global-budget invariants rather than weakening them.

---

**Design decision summary:** one immutable global budget epoch; signed Lease registrations; non-reclaimable per-Lease reservations; one shared global counter and lock; atomic per-Lease accounting at receipt commit; global fail-closed recovery. This is the smallest model that gives a clear, testable `Σ used <= Σ reserved <= global limit` argument.
