# E4.7 Dedicated TPM NV Counter Experiment Design v0.1

**Status:** Design only; no TPM state changes authorized by this document.  
**Target:** Dell Pro Tower QCT1250 / Intel Core i7-14700 / Nuvoton NPCT75x TPM 2.0, firmware 7.2.5.1.  
**Evidence:** User-run E4.1–E4.6 diagnostics.  
**Scope:** Select a safe dedicated test-index design and define the preflight/acceptance conditions.  
**Out of scope:** Defining an NV index, incrementing a counter, undefining an index, changing BIOS/TPM configuration, clearing TPM, or modifying the 16 existing NV indices.

## 1. E4.6 results recorded

| Property | Reported value | Correct interpretation |
|---|---:|---|
| `TPM_PT_NV_COUNTERS_MAX` | 0 | No fixed counter-index maximum; constrained by available NV memory pool. |
| `TPM_PT_NV_INDEX_MAX` | 2048 | Maximum data area size of one NV index, in bytes. |
| `TPM_PT_ORDERLY_COUNT` | 255 | `MAX_ORDERLY_COUNT` (2^8 - 1). For an `ORDERLY=SET` counter, the next increment after its low 8 bits equal `0xFF` causes an NV update. |
| `TPM_PT_NV_BUFFER_MAX` | 1200 | Maximum data size in one NV read/write/extend/certify command, not the per-index capacity. |
| `TPM_PT_HR_NV_INDEX` | 16 | Current number of defined NV indices; matches the 16 handles enumerated in E4.4/E4.5. |
| `TPM_PT_NV_COUNTERS` | 4 | Current number of NV indices with `TPM_NT_COUNTER`; matches E4.5 decoding. |
| `TPM_PT_NV_COUNTERS_AVAIL` | 9 | Estimate of additional counters that may be defined with `TPMA_NV_ORDERLY=SET`; not a general free-slot count and may become invalid after NV allocation changes. |
| `TPM_PT_NV_WRITE_RECOVERY` | 0 | Current reported approximate wait, in milliseconds, before another NV-modifying command is accepted. This does not prove unlimited write rate or absence of wear/latency constraints. |

All eight TBS submissions and TPM response codes were `0x00000000`. The query was read-only. `MoreData=True` is not itself a failure: the requested properties were returned with matching property identifiers; the capability interface reports whether additional property entries exist after the returned range.

## 2. Correct interpretation of counter durability

There are two relevant counter configurations:

- `TPMA_NV_ORDERLY` **CLEAR**: the counter update must be persistent when `TPM2_NV_Increment` completes successfully. This is the simpler semantics for testing synchronous persistence, at the cost of requiring an NV update for each increment.
- `TPMA_NV_ORDERLY` **SET**: the TPM may maintain a volatile count and periodically persist it. `TPM_PT_ORDERLY_COUNT=255` means `MAX_ORDERLY_COUNT=0xFF`; when the low-order count bits equal this value, the next increment causes an NV write. After an abnormal shutdown, TPM counter semantics must prevent rollback; the effective count may advance to a safe boundary rather than preserving the last volatile value exactly.

For a first experiment whose purpose is to verify that a successful increment remains visible after restart, an `ORDERLY=CLEAR` counter is the easier-to-interpret candidate. This is a design preference, not proof that this TPM will accept the proposed index or that Windows/TBS will authorize its mutation.

## 3. Capacity and existing-index constraints

E4.5 observed 16 existing indices, including four counters. E4.6 reports `NV_COUNTERS_MAX=0`, so there is no fixed numeric cap; actual capacity depends on the implementation's NV memory pool. `NV_COUNTERS_AVAIL=9` applies only to additional `ORDERLY=SET` counters. It does **not** guarantee capacity for an `ORDERLY=CLEAR` counter.

The existing 16 indices must be treated as platform/system state. Do not read their data areas, change attributes, undefine them, or use them for experiments. E4.7 must select a new handle in an owner-controlled namespace only after a fresh `TPM2_NV_ReadPublic` check establishes that the candidate handle is unused. A candidate handle is not frozen by this document.

## 4. Proposed test-index profile (not yet executable)

| Field | Proposed value | Rationale |
|---|---|---|
| Index type | `TPM_NT_COUNTER` | Hardware monotonic counter semantics. |
| Data size | 8 bytes | Required counter data width. |
| Name algorithm | SHA-256 (`0x000B`) | Matches the observed TPM support and existing index metadata. |
| `TPMA_NV_ORDERLY` | CLEAR | Synchronous persistence after successful increment. |
| Authorization | Dedicated test-only authorization value or policy; no reuse of production/system secrets | Limit test scope. Exact authorization scheme must be reviewed before implementation. |
| Read / increment permissions | Minimum required for the experiment; no broad PP/OWNER access unless required and explicitly justified | Least privilege. |
| Handle | Not selected yet | Must be in an appropriate owner-controlled range and confirmed unused immediately before definition. |

Do not implement this profile by modifying an existing NV index. `TPM2_NV_DefineSpace` is an allocation/write operation and requires explicit authorization and a recovery plan.

## 5. Required preflight before any write experiment

The following items must be resolved and documented before a separate explicit approval for E4.7 execution:

1. Confirm the exact TPM device and firmware identity again immediately before the experiment.
2. Confirm a new candidate NV handle is unused using `TPM2_NV_ReadPublic` (an expected handle-not-found response is acceptable for the candidate only).
3. Determine which hierarchy will own the test index and which authorization value/policy will be used. Do not retrieve, print, or expose existing owner/platform authorization secrets.
4. Confirm the exact `TPMA_NV` flags and verify reserved bits are zero.
5. Confirm the test index can be removed using only its own test authorization and the selected hierarchy authorization, without touching system indices.
6. Record a pre-test inventory of all 16 existing handles and their public-area Names; after the experiment, confirm those handles and Names are unchanged.
7. Define stop conditions for TPM errors, unexpected handle collisions, power loss, authorization lockout, or an unexpected change in the NV inventory.
8. Establish that the experiment will not call `TPM2_Clear`, alter firmware, change BIOS settings, or undefine any non-test index.
9. Document that the TPM property `NV_WRITE_RECOVERY=0` is only a current approximate wait property, not a write-endurance guarantee.

## 6. Proposed experiment sequence (requires separate approval)

This is a future sequence, not a command list to execute now:

- P0: Capture a fresh read-only TPM identity, properties and NV handle inventory.
- P1: Define exactly one new test-only `ORDERLY=CLEAR` counter.
- P2: Read its public area and confirm its type, attributes, size, Name and policy.
- P3: Read the initial counter value.
- P4: Perform one increment with the dedicated test authorization; record TBS return code and TPM response code separately.
- P5: Read the counter and confirm it increased by exactly one.
- P6: Perform a normal OS restart; read again and confirm the value did not decrease.
- P7: If separately approved, perform a controlled abnormal-power-loss experiment only after assessing device/data loss risk. Do not use forced power-off as an initial test.
- P8: Undefine only the test index, verify its handle is absent, and confirm all 16 pre-existing handles and Names are unchanged.

The first experiment should stop at P6. Abrupt-power-loss testing is a separate, higher-risk experiment.

## 7. Security claims this experiment can and cannot support

If the test succeeds, it can support a narrow claim: on this specific TPM/firmware/platform, a dedicated `ORDERLY=CLEAR` TPM NV counter increment is observable after a normal restart, with the documented authorization and command path.

It does not establish:

- atomicity between a TPM counter increment and an external database/tool side effect;
- exactly-once external execution;
- resistance to a compromised OS with authorization access;
- resistance to physical attacks or all TPM implementation flaws;
- TEE isolation of the Agent executor;
- general behavior across other TPM vendors/firmware versions;
- suitability or performance for high-frequency Agent budget accounting.

## 8. Acceptance gate

E4.7 design is ready for an implementation proposal only when Sections 3–5 are resolved. No TPM mutation is permitted merely because this design document exists. Any create/increment/delete commands require a separate, explicit execution approval after the exact handle, authorization, attributes and cleanup plan have been reviewed.
