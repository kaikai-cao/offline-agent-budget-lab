# E0.4 — Root-level budget reconciliation

## Scope

E0.4 adds an Issuer-signed allocation manifest and a root-level reconciler.
The manifest snapshots the exact set of leases issued by the in-memory Issuer
at a point in time. Creating the manifest freezes further lease issuance in
this E0 run, so later allocations cannot silently escape the signed inventory.
Each manifest entry binds `lease_id`, `grant_id`, allocated amount, and a digest
of the complete signed lease credential.

The reconciler checks the manifest and issuer signature, exact lease-bundle
coverage, lease credential digests, ledger-to-lease binding, executor receipt
signatures, hash-chain continuity, terminal-operation receipt coverage, and
per-lease/root-level budget accounting.

## Accounting semantics

- `committed_budget` is confirmed consumption.
- `reserved_budget` remains occupied because execution has not been finalized.
- `indeterminate_budget` remains occupied because the external outcome is unknown.
- `aborted` operations release their reservation and do not count as spent, under
the caller's assertion that no external effect occurred.
- `occupied_budget = committed + reserved + indeterminate`.

Statuses:

- `accepted`: every manifest lease is represented; lease, ledger and receipt
  checks pass; each chain matches an independent trusted head; no reserved or
  indeterminate operation remains.
- `incomplete`: a known lease bundle is missing, no independent chain-head
  anchor is supplied, or unresolved operations remain.
- `rejected`: signatures, credential bindings, chain/ledger consistency,
  duplicate or extra bundles, checkpoint comparisons, or budget checks fail.

## Trusted chain-head requirement

A hash chain authenticates links inside the submitted prefix, not the existence
of an omitted suffix. `TrustedChainHead` is an out-of-band expected tuple
(chain ID, length, head hash) supplied by an independent trusted source. It
must not simply be copied from the same untrusted receipt package under test.

This prototype does not implement a production checkpoint registry or prove
the provenance of that trusted input. If no independent anchor is supplied,
the report is `incomplete`, not `accepted`. If both local ledger and receipts
can be rolled back and no independent anchor exists, omitted offline
operations cannot be reconstructed from the remaining software state.

## Explicit limitations

- Issuer allocation state, local ledgers and receipt chains remain in-memory.
- The allocation manifest is a signed, issuance-closing inventory, not a
  durable transparency log or anti-rollback mechanism. The in-memory freeze is
  lost if the Issuer process is restarted or its state is rolled back.
- An executor signature is an assertion by the configured key, not TEE
  attestation or independent proof that a real database query occurred.
- This module does not implement ZK privacy, cross-process atomicity,
  distributed consensus, hardware anti-rollback, or a checkpoint registry.
- `accepted` is conditional on the correctness and trustworthiness of the
  supplied issuer key, complete manifest, evidence bundles and trusted heads.

## Reproduction

Run `run_tests.ps1` from the repository root. The full suite includes E0.1,
E0.2, E0.3 and E0.4 tests.
