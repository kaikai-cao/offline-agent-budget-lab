# E4.4 Read-only TPM command probe v0.1

## Context

The platform has already demonstrated:
- TPM 2.0 present, ready, enabled, activated, owned.
- Nuvoton NPCT75x family reported through Windows TPM metadata.
- Secure Boot enabled.
- `Tbsi_Context_Create` and `Tbsip_Context_Close` both returned `0x00000000`.
- TBS service enumeration was anomalous (`sc.exe query TBS` returned 1060), while the TBS API context call succeeded.

## Objective

Verify that the TBS context can submit selected non-mutating TPM 2.0 capability queries and inspect the TPM's currently advertised command set and current NV-index handle list.

## Commands

1. `TPM2_GetCapability(TPM_CAP_COMMANDS, property=0x130, propertyCount=64)`.
2. `TPM2_GetCapability(TPM_CAP_HANDLES, property=0x01000000, propertyCount=64)`.

The script checks the TBS API return separately from the TPM response code. This distinction is required because Microsoft documents that a TBS submission may succeed while the TPM command itself returns a TPM error.

## Interpretation limits

- Command advertisement is not proof that Windows/TBS permits an operation under the active command policy.
- The presence of `TPM_CC_NV_Increment` in the advertised command set does not prove that a later increment command would pass Windows/TBS policy or TPM authorization.
- No current NV handles does not prove there is no NV capacity.
- This stage does not test NV authorization, NV index definition policy, write locks, counter attributes, endurance, or power-failure behavior.
- This stage does not create or modify TPM NV state.

## Stop condition

Do not send an NV write or increment command in this stage. A later mutating test, if justified, must use a separately designed test index, explicit user confirmation, a verified cleanup/recovery plan, and exact accounting of persistent state changes.
