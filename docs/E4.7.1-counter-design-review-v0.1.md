# E4.7.1 — Dedicated TPM NV Counter Design Review v0.1

**Status:** design decision draft; no TPM write authorization granted  
**Platform under evaluation:** Dell Pro Tower QCT1250, Intel Core i7-14700, Nuvoton NPCT75x, TPM firmware 7.2.5.1  
**Evidence available:** E4.1–E4.6 user-run read-only results  
**Scope:** settle the candidate index, public attributes, authorization roles, preconditions, test sequence, and cleanup rules.  
**Out of scope:** executing `TPM2_NV_DefineSpace`, `TPM2_NV_Increment`, `TPM2_NV_UndefineSpace`, changing hierarchy authorization, modifying BIOS/TPM settings, or claiming end-to-end anti-rollback security.

---

## 1. E4.1–E4.6 facts relevant to this decision

The user's platform probes establish:

- TPM 2.0 is present, enabled, activated, owned, and Ready.
- Manufacturer ID text is `NTC`; manufacturer version is `7.2.5.1`; firmware metadata identifies `NPCT75x`.
- Secure Boot is enabled.
- A TBS context can be created and closed successfully (`0x00000000`). The Windows service enumeration anomaly remains, but it did not prevent TBS API context creation or the successful commands below.
- The TPM advertised `TPM_CC_NV_Increment`, `TPM_CC_NV_Read`, and `TPM_CC_NV_ReadPublic`.
- `TPM2_NV_ReadPublic` succeeded for all 16 currently enumerated NV indexes.
- E4.6 returned: `TPM_PT_NV_COUNTERS_MAX=0`, `TPM_PT_NV_INDEX_MAX=2048`, `TPM_PT_ORDERLY_COUNT=255`, `TPM_PT_NV_BUFFER_MAX=1200`, `TPM_PT_HR_NV_INDEX=16`, `TPM_PT_NV_COUNTERS=4`, `TPM_PT_NV_COUNTERS_AVAIL=9`, `TPM_PT_NV_WRITE_RECOVERY=0`.

These are capability and metadata observations. They do **not** yet establish that a new non-orderly Counter can be allocated, that Owner authorization is available to this test, or that the counter is protected against deletion by a privileged actor.

## 2. Corrections that must be carried forward

### 2.1 `NV_COUNTERS_AVAIL=9` is not capacity evidence for this design

The property counts an estimated number of additional indexes that can be defined with `TPM_NT_COUNTER` and `TPMA_NV_ORDERLY` **SET**. The proposed index intentionally has `TPMA_NV_ORDERLY` **CLEAR**. Therefore the value 9 must not be used as evidence that this candidate can be allocated. `TPM_PT_NV_COUNTERS_MAX=0` means there is no fixed Counter-count maximum; the effective limit is the available NV memory pool. A `TPM2_NV_DefineSpace` attempt can still fail with `TPM_RC_NV_SPACE`.

### 2.2 `NV_WRITE_RECOVERY=0` is not a wear or endurance guarantee

It is an approximate delay before another NV-modifying command is accepted. It says nothing by itself about endurance, performance under load, or unlimited write capacity.

### 2.3 `ORDERLY=CLEAR` has a specific persistence meaning

With `TPMA_NV_ORDERLY` CLEAR, the TPM must persist the index state after a command that updates the index completes successfully. This is why it is the candidate for the first controlled persistence test. It does not make a TPM state update atomic with an external database/tool operation, and it does not guarantee what happens when power fails during an in-flight command before the caller receives a response.

## 3. Candidate handle decision

**Candidate:** `0x01BFFFFE`  
**Range:** Owner NV range `0x01800000`–`0x01BFFFFF`.

The published TCG Registry of Reserved TPM 2.0 Handles and Localities assigns this unallocated-by-TCG range to Owner-defined NV indexes. The registry explicitly says the convention is not enforced by the TPM and does not itself allocate NV space. Owner-specific indexes may be used by OS or application software. Thus the range is appropriate for a private lab/application index, but the exact value is only a project convention.

Why choose the high-end candidate `0x01BFFFFE`:

- It is inside the Owner range.
- It does not collide with any of the 16 handles in the user's E4.5 snapshot.
- It is a single fixed candidate, so the experiment will fail closed rather than silently selecting another index if it is occupied.

**Availability is not yet frozen.** The E4.7.2 read-only preflight must query `TPM_CAP_HANDLES` again and verify that this exact handle is absent immediately before any separately approved write phase. A read-only check cannot reserve the handle; another local component could allocate it between preflight and definition. `TPM2_NV_DefineSpace` must still be treated as the final atomic collision check.

## 4. Candidate NV Public Area

| Field | Frozen candidate | Rationale |
|---|---|---|
| `nvIndex` | `0x01BFFFFE` | Owner-assigned range; subject to fresh availability check |
| `nameAlg` | `TPM_ALG_SHA256 = 0x000B` | Same name algorithm used by all 16 observed indexes; widely interoperable |
| `dataSize` | `8` | Required size for `TPM_NT_COUNTER` |
| `authPolicy` | empty | This first lab test uses an index authorization value, not a policy session |
| `TPMA_NV` | `0x00040014` | `AUTHREAD (0x00040000) | AUTHWRITE (0x00000004) | COUNTER (0x00000010)` |
| `ORDERLY` | CLEAR | Synchronous persistence after successful update command |
| `PLATFORMCREATE` | CLEAR | Index is defined using Owner hierarchy, not Platform hierarchy |
| `POLICY_DELETE` | CLEAR | Allows cleanup through ordinary `TPM2_NV_UndefineSpace` with Owner authorization |
| `NO_DA` | CLEAR | Do not opt this test index out of TPM dictionary-attack handling; use a high-entropy index auth and avoid wrong-auth trials |
| `WRITTEN` | initially CLEAR / TPM-managed | Do not set this bit in the requested public attributes |

The bit mask calculation is:

`0x00040000 | 0x00000004 | 0x00000010 = 0x00040014`.

The mask intentionally excludes `TPMA_NV_ORDERLY (0x04000000)`, `TPMA_NV_PLATFORMCREATE (0x40000000)`, and `TPMA_NV_POLICY_DELETE (0x00000400)`.

At definition time, the TPM stores the supplied index `authValue`; it must be no longer than the SHA-256 digest size (32 bytes). The later `NV_Read` and `NV_Increment` operations are to use the index authorization because `AUTHREAD` and `AUTHWRITE` are set. The Owner hierarchy authorization is a separate credential, needed to define and later undefine the index.

## 5. Authorization model and hard preconditions

There are two distinct secrets/roles:

1. **Owner hierarchy authorization** — required for `TPM2_NV_DefineSpace` and for cleanup with `TPM2_NV_UndefineSpace` because this index is Owner-created (`PLATFORMCREATE` CLEAR).
2. **Index authValue** — a fresh 32-byte random value supplied at definition and later used for `NV_Read` and `NV_Increment`.

Do not assume that `Get-Tpm`'s blank `OwnerAuth` display proves that Owner authorization is empty or known. The next read-only preflight must query:

- `TPM_PT_PERMANENT` (`0x00000200`): bit 0 is `ownerAuthSet`; bit 9 is `inLockout`.
- `TPM_PT_STARTUP_CLEAR` (`0x00000201`): bit 1 is `shEnable`, which must be SET for Owner hierarchy use.

Interpretation:

- `shEnable=0`: stop. Do not try to enable the hierarchy or switch to Platform authorization as an improvised workaround.
- `inLockout=1`: stop. Do not send authorization trials.
- `ownerAuthSet=1`: Owner authorization has been changed since the last `TPM2_Clear`; its actual value is not disclosed by this property. Do not guess it.
- `ownerAuthSet=0`: this only means the Owner auth-change operation has not been executed since the last Clear; it is not a substitute for an explicit authorization plan. The write phase still requires the user to confirm which Owner authorization value will be used. Never test candidate passwords by repeated attempts.

The first write experiment cannot proceed until Owner authorization and a recoverable cleanup path are known. Do not call `TPM2_HierarchyChangeAuth`, `TPM2_Clear`, `TPM2_HierarchyControl`, or any command that changes hierarchy state as part of this lab setup.

## 6. Security interpretation: what this experiment will and will not prove

If the test succeeds, it can establish on this particular physical TPM that:

- the chosen Owner-range NV index can be defined with the selected public attributes;
- an authorized `NV_Increment` succeeds;
- after a successful response, the counter can be read as the expected value;
- after a normal Windows restart, the counter value remains unchanged for this `ORDERLY=CLEAR` index.

It will **not** establish:

- protection against an attacker who can use Owner authorization to undefine and recreate the index;
- protection against TPM clear, firmware/platform re-provisioning, or physical replacement;
- that the TPM update and an external tool/database side effect are one atomic transaction;
- remote attestation of the code that requested the increment;
- production-grade TEE isolation or a formal anti-rollback proof.

This distinction is critical. An Owner-created index with `POLICY_DELETE` CLEAR is deliberately cleanable through Owner authorization. If the adversary controls or can obtain that authorization, the adversary may be able to remove and recreate the index, resetting its state. Therefore this initial experiment is a **TPM persistence primitive test**, not yet a complete defense against a privileged host attacker. A later security design would need to evaluate the Platform hierarchy, a deletion policy, access mediation, or a separate trusted execution boundary. No such escalation is authorized by this document.

## 7. Planned experiment sequence — not executable yet

Only after E4.7.2 preflight passes and the user separately approves the exact write operation:

1. Save a fresh baseline of all current NV handles and each existing index's public `Name`.
2. Recheck `0x01BFFFFE` is absent, `shEnable` is SET, `inLockout` is CLEAR, and the Owner authorization path is known.
3. Generate a fresh 32-byte index authValue using a cryptographic RNG. Do not print it. Store it outside Git in a user-protected local secret file; do not put it in README, logs, command history, or test results.
4. Define exactly one index at `0x01BFFFFE` with the Public Area in Section 4 and Owner hierarchy authorization.
5. Immediately run `NV_ReadPublic` and compare every public field against the frozen values. If any field differs, stop; do not increment.
6. Before first increment, an authorized `NV_Read` may return `TPM_RC_NV_UNINITIALIZED`; this is expected because `WRITTEN` starts CLEAR. Do not treat this as an increment failure.
7. Execute exactly one `NV_Increment`. Require both TBS submission success and TPM response success. Then `NV_Read` and require the eight-byte big-endian value `0000000000000001`.
8. Perform a normal Windows restart (not a forced power cut). Re-read the Public Area and counter; require the value remains 1.
9. Record the result and compare the original 16 NV handle/Name pairs to the post-test snapshot. Any unexpected difference is a stop condition.
10. Cleanup only the exact test handle with `TPM2_NV_UndefineSpace` and the known Owner authorization. Verify `ReadPublic` now reports the index absent. Never run a bulk undefine, TPM clear, or cleanup over a range.

The first experiment uses one increment only. It does not perform repeated writes, benchmark NV endurance, or test power loss in the middle of the command. A forced-power-loss test, if ever justified, is a separate experiment requiring its own risk review.

## 8. E4.7.2 read-only preflight acceptance gates

All conditions below must be met before preparing a write command:

- [ ] TBS context creation and close succeed.
- [ ] `TPM_CAP_HANDLES` snapshot succeeds and the candidate `0x01BFFFFE` is absent.
- [ ] The 16 known E4.5 baseline handles are still present with unchanged NV `Name` values, or any difference is explained before proceeding.
- [ ] `TPM_PT_PERMANENT` is read and `inLockout` is CLEAR.
- [ ] `TPM_PT_STARTUP_CLEAR` is read and `shEnable` is SET.
- [ ] Owner authorization value and recovery/cleanup plan are known without password guessing.
- [ ] The user has reviewed the exact public attributes and explicitly approved the later `NV_DefineSpace` and one `NV_Increment` operations.

If any condition is missing, the result is **BLOCKED**, not “probably okay.”

## 9. Decision

**E4.7.1 design decision:** retain `0x01BFFFFE` as the single candidate Owner NV handle; retain the public attributes `0x00040014`, SHA-256, 8-byte Counter, and `ORDERLY=CLEAR` as the candidate template. Do not create it yet.

**Next stage:** E4.7.2 is a strictly read-only preflight of the candidate handle, Owner hierarchy state, lockout state, and the original 16-index baseline. Only after that report is reviewed should a separate write-operation proposal be prepared.
