# E3 Architecture Freeze v0.1

## 面向多 Agent 离线工具执行的预算约束、可信状态与最终对账

**状态：** 候选架构冻结稿；不是安全证明，也不是生产实现规范  
**依据：** E0.1–E0.4、E1、E1.1、E2 的用户本地测试结果（累计 100/100）  
**本阶段范围：** 协议流程、状态机、失败语义、信任假设、硬件能力需求和进入实机评估的门槛。  
**本阶段不做：** 新代码、真实 TEE/安全元件集成、ZK 电路、数据库持久化实现、生产部署。

## 1. E2 已验证事实与尚未验证事项

### 1.1 已由当前实验支持的结论

| 编号 | 观察 | 证据边界 |
|---|---|---|
| E2-F1 | 单个软件账本实例可以在进程内阻止同一 operation ID 重放，并通过锁避免本实例内并发超额预留 | 仅限当前 Python 单进程对象模型 |
| E2-F2 | 复制/重建普通软件账本后，两个副本可以各自接受本地合法消费 | 证明当前软件模型可被分叉，不代表所有软件部署方式都相同 |
| E2-F3 | 共享在线原子状态抽象可以在多个执行副本之间串行化消费 | 当前是测试用抽象，不是已验证的分布式一致性服务 |
| E2-F4 | 单调状态模拟器可以拒绝跨设备使用、状态重建后的重复消费，并在不可用时 fail closed | 仅验证抽象接口和测试模型，不构成真实硬件安全证据 |
| E2-F5 | 执行者公钥必须来自证据包之外的可信配置；证据包不能自行选择验证公钥 | 已通过 E1.1 回归测试 |
| E2-F6 | 最终对账需要独立可信链头；哈希链本身不能证明提交的是完整链尾 | 仅针对当前收据/锚点模型 |

### 1.2 当前不能声称的性质

- 尚未证明真实 TEE、TPM、安全元件或安全启动链能满足本设计要求。
- 尚未证明硬件状态更新与外部工具副作用可以原子提交。
- 尚未实现多机器、分布式数据库或多可用区的生产级全局原子分配器。
- 尚未证明外部数据库返回结果的真实性、完整性或新鲜度。
- 尚未提供 Agent 身份、委派路径、预算金额或执行内容的隐私保护。
- 100/100 单元测试通过仅表示已实现测试通过，不是统计意义上的攻击成功率，也不是安全证明。

## 2. 系统目标与最小场景

根授权方持有资源预算 `B`。它在线创建若干互不重叠的离线额度 Lease，并分别绑定到指定的可信执行设备。Agent 在无法连接中心预算服务时，仍可调用本地可达的数据访问工具；每次调用消耗由可信执行组件计算的 `cost_units`。网络恢复后，提交分支证据并完成全局对账。

**“离线”定义：** Agent/执行设备无法访问中心分配与对账服务，但仍能访问本地或边缘侧工具。若工具本身不可达，则本次操作不能执行。

v1 只使用整数型 `cost_units`。成本规则由受信执行组件根据工具策略计算，不接受 Planner 在请求中自行申报成本。暂定一次成功查询消耗一个单位。

### 2.1 全局预算关系

根预算：

\[
B \in \mathbb{N}
\]

在线分配给各 Lease 的额度为 `b_i`：

\[
\sum_{i=1}^{n} b_i \leq B
\]

每个 Lease 的已占用预算由其执行状态计算。对 Lease `i`：

\[
occupied_i = committed_i + reserved_i + indeterminate_i
\]

其中：

- `committed`：已确认执行并扣费；
- `reserved`：已预留额度，操作结果尚未终结；
- `indeterminate`：可能已经产生外部效果，但执行结果不能确定；
- `aborted`：只有在能够可靠证明外部效果没有发生时，才释放预留额度，不计入占用。

每个 Lease 必须满足：

\[
occupied_i \leq b_i
\]

全局保守上界：

\[
\sum_i occupied_i \leq B
\]

**重要：** 离线期间不得把尚未完成最终对账的 Lease 剩余额度重新分配给其他 Agent。否则中心无法知道原离线分支是否已经消费了这部分额度。未结算余额必须继续视为被占用/锁定额度。

## 3. 参与方和信任边界

| 参与方 | 职责 | 信任假设 |
|---|---|---|
| Root Authority / Issuer | 管理根预算、原子分配子额度、签发 Allocation Manifest 和 Lease | 必须有唯一、持久、不可分叉的权威状态域；若多实例部署，需要真实的线性化/共识保障 |
| Agent / Planner | 生成工具调用意图、携带授权 | 不可信；不能自行决定预算成本、执行者公钥或最终执行结果 |
| Trusted Executor | 验证请求、执行工具调用、与可信状态存储交互、签发收据 | 其代码身份、密钥和状态完整性在硬件信任假设内可信 |
| Secure State Provider | 提供防回滚、设备绑定、原子状态推进能力 | 需要真实硬件/平台保证；模拟器不等于实现 |
| Tool / Data Service | 执行具体工具操作，最好支持 operation ID 幂等去重或状态查询 | 其副作用与 Executor 状态之间默认不具备原子事务；工具语义必须单独定义 |
| Reconciler | 验证 Manifest、设备证明、收据、状态计数器/链头并汇总预算 | 验证逻辑与信任根必须独立于待验证证据包 |
| Attestation Verifier / Trust Registry | 验证设备身份、Executor 测量值和公钥注册 | 根证书、撤销信息和策略更新渠道属于额外信任基础 |

### 3.1 明确的攻击者能力

攻击者可控制 Agent/Planner，并可读取、复制、修改、恢复普通文件和软件账本；可并发启动多个 Agent 进程；可重放旧请求和旧收据；可断网、断电或在工具调用前后杀死 Executor；可提交不完整证据包。攻击者不能在安全假设成立时提取硬件不可导出的私钥、伪造有效硬件证明或回滚硬件保护的单调状态。

本架构不假设能够抵御硬件漏洞、芯片供应链攻击、可信执行环境侧信道、平台固件被攻陷或根授权方恶意签发额度。若这些攻击进入威胁模型，需要另行设计。

## 4. 架构决策

### ADR-E3-01：采用“在线预分配 + 设备绑定离线消费 + 最终对账”

**选择：** 根授权方在线分割预算，签发不可重叠 Lease；每个 Lease 绑定一个受信执行设备/安全状态域；设备断网期间只允许在本 Lease 额度内执行；恢复连接后以设备证明、签名收据和独立链头完成对账。

**理由：**

1. 预算分片使全局总额在分配时满足 `Σb_i ≤ B`；离线阶段不需要不同 Agent 之间持续协调预算。
2. 单个 Lease 的复制/回滚由设备绑定和硬件防回滚状态承担，而不是依靠普通文件或哈希链。
3. 证据和最终对账负责证明哪些操作已经记录、哪些仍不确定，并检测缺失、分叉或超额。

**不选择：**

- 纯软件本地余额作为离线防双花机制：E1 已展示其可被状态复制/重建绕过。
- 每次消费都调用共享在线余额服务：可以提供在线唯一性，但网络不可用时无法继续执行，与离线需求冲突。
- 现在直接加入 ZK：ZK 可以隐藏额度/身份并证明关系，但不能单独防止普通状态回滚或同一凭证被分叉消费。

### ADR-E3-02：一个 Lease 对应一个硬件安全状态域

v1 中每份 Lease 只能由一个设备绑定的可信执行实例消费。Lease 凭证必须绑定：

- `lease_id` 和 `manifest_id`；
- `device_id` 或硬件信任域标识；
- `executor_public_key_hash`；
- `executor_measurement` / 允许的代码版本摘要；
- `tool_id`、`schema_hash` 和成本策略版本；
- `allocated_budget` 与 `cost_unit`；
- 根授权签名及签发序号。

Planner/Agent 的身份可以与 Executor 不同。不能要求 Holder 公钥与 Executor 公钥相同；Reconciler 必须从独立可信注册表/配置得到预期 Executor 公钥，并验证设备证明把该公钥绑定到允许的执行代码和设备。

### ADR-E3-03：不承诺离线即时撤销和未结算额度回收

Lease 一经交付，中心在设备断网时无法保证立即撤销。v1 不宣称离线即时撤销。Lease 有效期只有在设备提供可信时间能力时才可作为安全条件；否则仅作为提示字段，不作为防超支依据。

在所有分支完成最终对账前，不重新分配未使用额度。分支丢失或设备永久不可用时，剩余额度保持锁定/保守计费，不能通过普通超时自动回收。

## 5. 协议流程

### Phase 0：在线额度分配与设备注册

1. Root Authority 在一个权威原子状态域中检查根预算剩余量。
2. Authority 为每个目标设备创建 `lease_id`，分配互不重叠的 `b_i`。
3. 设备在安全环境内生成或持有不可导出的 Executor 签名密钥。
4. Attestation Verifier 验证设备证明、Executor 测量值和公钥绑定；将可信关系写入独立 Trust Registry。
5. Issuer 将 `lease_id`、预算、工具策略摘要、设备标识、Executor 公钥摘要和代码测量值写入 Lease 并签名。
6. Issuer 将完整 Lease 集合写入 Allocation Manifest，包含 `manifest_id`、根预算、所有 Lease 摘要、总分配额度、签发序号和签名。
7. Manifest 成功持久化并锚定后，进入离线期。后续额度变化必须产生新版本/新 Manifest，不能悄悄追加到旧 Manifest。

### Phase 1：离线启动与本地状态恢复

1. Executor 验证 Issuer 签名、Lease 摘要、Manifest 归属及策略版本。
2. Executor 通过设备绑定密钥证明自身身份；不得使用证据包自带公钥作为信任根。
3. Secure State Provider 读取当前硬件单调版本 `v`、Lease 绑定摘要、剩余额度、操作日志头 `h`。
4. 检查硬件状态版本与持久化日志是否匹配。若状态缺失、版本回退、Lease 绑定不一致或硬件不可用，必须 fail closed，停止新操作。
5. 如果平台不能提供可信时钟，则不在离线阶段依赖 `expires_at` 做安全决策。

### Phase 2：一次离线工具操作

每次操作使用唯一 `operation_id`，并绑定：`lease_id`、`tool_id`、`schema_hash`、`request_hash`、`context_hash`、成本策略版本和 `cost_units`。

**步骤 A：授权检查**

- 验证工具和 Schema 属于 Lease 授权范围；
- 由可信 Executor 计算 `cost_units`；
- 拒绝重复的 `operation_id`；
- 检查剩余额度足够。

**步骤 B：先预留，再调用工具**

Executor 调用 Secure State Provider 的原子状态推进接口：

`advance(expected_version, new_state_digest, reservation_record)`

成功后，硬件保护状态中已持久记录该 `operation_id`、请求摘要、成本、预留状态和新版本/计数器。该动作必须在工具副作用之前完成。

**步骤 C：持久化调用意图并调用 Tool**

1. 在调用外部 Tool 之前，Executor 必须先将操作从 `RESERVED` 原子推进到 `DISPATCHED`，并把 `operation_id`、`request_hash` 和新安全计数器持久绑定。
2. 只有在 `DISPATCHED` 状态持久成功后，才允许把请求发送给 Tool。这样，恢复时看到仍为 `RESERVED` 且不存在 `DISPATCHED` 记录，才能证明调用尚未开始。
3. 如果 Tool 支持幂等键，传入 `operation_id` 和 `request_hash`；相同 ID、相同请求重复提交应返回同一操作状态/结果，不得重复产生副作用。相同 ID 但不同请求摘要必须拒绝。
4. 如果 Tool 不支持幂等键或状态查询，Executor 在调用结果不确定时不得自动重试；必须保守标记为 `INDETERMINATE`。

**步骤 D：结束状态**

- 明确成功：可信状态更新为 `COMMITTED`，保留预算扣减；生成绑定结果摘要的签名收据。
- 明确未产生副作用且工具语义能证明：更新为 `ABORTED`，允许释放该次预留额度。
- 超时、进程崩溃、连接中断或无法判断工具是否已执行：更新/恢复为 `INDETERMINATE`；预算继续占用，不自动退款、不盲目重试。

**步骤 E：生成证据**

Executor 使用设备绑定密钥签署收据。收据至少包含：

`manifest_id, lease_id, device_id, operation_id, sequence, secure_counter, tool_id, schema_hash, request_hash, context_hash, cost_units, status, result_hash(optional), previous_receipt_hash, state_digest, executor_key_id`。

收据签名只证明受信 Executor 对这些字段作出了签名声明；对于外部数据真实性、查询结果正确性或外部副作用是否真实发生，仍需要相应 Tool/数据源证据或受信执行路径。

### Phase 3：断电/崩溃恢复

恢复时必须读取硬件保护的最新计数器、状态摘要和操作日志头，而不是信任磁盘快照。

| 崩溃点 | 恢复判定 | 预算处理 | 是否允许自动重试 |
|---|---|---|---|
| 预留前 | 没有可信预留记录 | 不扣预算 | 可重新发起 |
| 预留成功、工具调用前 | 若可信日志可证明未调用 | 可转 `ABORTED` 并释放 | 可在新 operation ID 下重试 |
| 工具请求已发送、响应未收到 | 外部效果未知 | `INDETERMINATE`，继续占用 | 只有 Tool 按 operation ID 提供可靠去重/状态查询时才可恢复同一操作 |
| 工具成功、状态提交前 | 外部效果可能已发生 | `INDETERMINATE`，继续占用 | 不可盲目重试 |
| 状态提交后、收据上传前 | 从可信日志重建收据 | 按 `COMMITTED` 计费 | 不重新执行工具 |
| 安全状态不可用/计数器异常 | 无法建立可信状态 | 保守占用未结算额度并停止执行 | 否，fail closed |

**核心边界：** 普通 TEE 单调计数器无法自动让外部数据库事务与硬件状态更新成为一个原子事务。除非 Tool 本身参与同一事务或提供可靠幂等/状态查询协议，否则不能承诺跨硬件和外部工具的 exactly-once 副作用。v1 采用“先预留、结果不确定则不退款”的保守语义。

### Phase 4：重新联网与最终对账

每个设备分支提交：

- Lease 和所属 Manifest；
- 完整收据链；
- 当前硬件状态报价/证明（fresh quote），其中绑定设备身份、Executor 测量值、当前安全计数器、Lease 摘要和最终日志头；
- 可取得的 Tool 端 operation 状态/幂等记录；
- 所有未决操作的状态说明。

Reconciler 使用独立 Trust Registry 和 Issuer 公钥验证，而不是相信证据包自带的公钥。验证至少包括：

1. Manifest 签名与完整 Lease 集合；
2. 分配总额 `Σb_i ≤ B`；
3. 每份 Lease 与设备、Executor 密钥、测量值绑定；
4. 收据签名、序号、哈希链接和 operation ID 唯一性；
5. 可信硬件最终计数器/日志头与收据链头一致；
6. `COMMITTED + RESERVED + INDETERMINATE` 的保守预算占用不超过 Lease 额度；
7. 各 Lease 占用总和不超过根预算；
8. 不存在缺失分支、分叉、回滚或未解决的工具效果不确定性。

只有满足全部接受条件，才能返回 `ACCEPTED`。分支缺失、设备离线、无法取得可信链头或存在未决操作，返回 `INCOMPLETE`。签名/证明无效、预算超额、设备或执行代码不匹配、计数器/链头冲突，返回 `REJECTED`。

## 6. 状态机

### 6.1 Lease 状态

`ISSUED -> DEVICE_BOUND -> ACTIVE -> RECONCILIATION_PENDING -> RECONCILED`

异常路径：

- `DEVICE_BOUND` 或 `ACTIVE` 阶段发现证明/安全状态异常：`SUSPENDED`；
- 设备丢失或状态无法恢复：保持 `RECONCILIATION_PENDING`，不得自动释放预算；
- `RECONCILED` 后，才允许 Authority 根据已验证的剩余额度制定新分配。

v1 不提供离线即时 `REVOKED` 保证。在线撤销只能在设备重新取得可信新鲜状态或下一次联网检查时生效。

### 6.2 单次操作状态

```text
NEW
  └─ atomic budget reservation ─────> RESERVED
       ├─ abort before dispatch ─────> ABORTED
       └─ durable dispatch marker ───> DISPATCHED
            ├─ effect confirmed ─────> COMMITTED
            ├─ no-effect proven ─────> ABORTED
            └─ outcome uncertain ────> INDETERMINATE
```

`DISPATCHED` 必须在任何外部 Tool 调用之前持久化。恢复时若处于 `RESERVED` 且没有 dispatch marker，可证明调用未开始；一旦进入 `DISPATCHED`，除非 Tool 提供可靠状态查询，否则必须保守按 `INDETERMINATE` 处理。

合法终态：`COMMITTED`、`ABORTED`、`INDETERMINATE`。`DISPATCHED` 是非终态，仍占用预算，不允许重复派发。`INDETERMINATE` 不得由 Agent 自行改成 `ABORTED`；只能依据可信 Tool 状态证据和受信恢复逻辑解决。

## 7. 必须由真实硬件/平台满足的能力

以下是采购或实机适配前的要求清单，不代表任何特定产品已经满足。

| 硬件能力 | 最低要求 | 缺失时的影响 |
|---|---|---|
| 设备绑定密钥 | 私钥不可导出；签名行为绑定到授权设备/安全域 | 状态或密钥可能被复制到其他设备 |
| 远程证明 | 能验证设备平台身份、启动链/执行代码测量值，并将公钥绑定到测量值 | Reconciler 无法确认收据来自预期执行代码 |
| 防回滚持久状态 | 在断电、重启和恢复旧磁盘快照后，仍可检测旧状态 | E1-02/E1-03 类攻击仍成立 |
| 单调版本/计数器 | 可防止状态版本倒退，并能绑定 Lease 摘要和日志头 | 无法可靠检测旧状态恢复和日志回退 |
| 原子状态推进 | 预留记录与单调版本推进具有可恢复的原子语义 | 崩溃可能造成预算状态和操作日志不一致 |
| 并发串行化 | 同一安全域多线程/多进程更新不可重复成功 | 同设备并发仍可能超额消费 |
| 状态新鲜性 | 对账时可生成带随机挑战的最新状态证明 | 旧报价可能被重放，不能证明当前状态 |
| 密钥/测量值生命周期管理 | 支持版本策略、更新、撤销或替换流程 | 代码漏洞或密钥泄露后无法安全迁移 |
| 可选可信时间 | 若离线 TTL/时间撤销是安全目标，需要抗回拨时钟 | 普通系统时间不能作为离线撤销依据 |

**适配评估必须逐项取证：** 平台文档、API 行为、可运行原型、崩溃/回滚测试和安全边界。不能仅凭“支持 TPM/TEE/安全启动”标签就认定上述能力全部具备。

## 8. Tool 端必须满足的接口条件

预算硬件状态和外部工具不是同一个事务域。v1 优先要求 Tool 支持：

1. 接收唯一 `operation_id`；
2. 对同一 `operation_id` 和相同 `request_hash` 提供幂等行为；
3. 对相同 ID 但不同请求摘要拒绝；
4. 可按 operation ID 查询操作是否已接受/完成；
5. 提供可用于审计的状态摘要或签名回执（能力可选，但有则更强）。

如果 Tool 不支持这些条件：

- Executor 仍可采取 at-most-once 的保守调用策略；
- 一旦调用结果不确定，就记录 `INDETERMINATE` 并继续占用预算；
- 禁止自动重试不具备幂等保证的操作；
- 对账不能将不确定操作伪装为成功或失败。

## 9. 安全目标与验收关系

| 目标 | 性质 | 依赖 | 失败时判定 |
|---|---|---|---|
| G1 全局预算守恒 | `Σ allocated ≤ B` 且 `Σ occupied ≤ B` | 在线权威原子分配 + 不重用未结 Lease | 超额即 REJECTED |
| G2 单 Lease 防超额 | `occupied_i ≤ b_i` | 防回滚状态 + 原子预留 + 并发串行化 | 超额即 REJECTED |
| G3 设备/执行者绑定 | 收据密钥属于已注册设备上的允许 Executor | 设备证明 + 独立 Trust Registry | 缺失则 INCOMPLETE，不匹配则 REJECTED |
| G4 防重放 | 同一 operation ID 最多产生一个 Tool 逻辑效果 | 硬件唯一状态 + Tool 幂等/去重 | 冲突即 REJECTED；不明则 INCOMPLETE |
| G5 日志完整性 | 提交链与可信最终硬件链头匹配 | 防回滚日志头 + fresh quote | 无链头则 INCOMPLETE；冲突则 REJECTED |
| G6 最终对账 | 每个已签发 Lease 都有可验证终态 | Manifest + 所有分支证据 | 分支缺失/状态不确定则 INCOMPLETE |
| G7 离线可用性 | 中心不可达时可在本地额度范围内执行 | 预分配 Lease + 可用安全设备 + 本地可达 Tool | 安全状态不可用时 fail closed |
| G8 隐私 | 隐藏不必要的身份、路径、额度和操作元数据 | 未来独立隐私层 | **本版本不提供** |

## 10. 失败语义和预算处置矩阵

| 事件 | 工具效果是否确定 | 预算处置 | 对账状态 |
|---|---|---|---|
| 授权检查失败，尚未预留 | 无效果 | 不占用 | 可记录拒绝事件 |
| 硬件预留前崩溃 | 无效果（若没有预留记录） | 不占用 | 需要确认状态连续性 |
| 预留后、Tool 调用前崩溃 | 只有可信日志能证明未调用时才确定无效果 | 可安全 Abort，否则 Indeterminate | 不确定时 INCOMPLETE |
| Tool 成功且有可信响应 | 已发生 | Committed | 可接受 |
| Tool 超时，无查询接口 | 不确定 | Indeterminate | INCOMPLETE |
| Tool 提供同 ID 幂等查询并证实完成 | 已发生 | Committed | 可接受 |
| Tool 提供同 ID 查询并证实未接受 | 无效果（需 Tool 语义保证） | 可 Abort | 可接受 |
| 硬件状态丢失或设备永久不可用 | 无法证明完整性 | 未结预算继续锁定/保守占用 | INCOMPLETE，不能自动回收 |
| Executor 密钥/证明无效 | 不可信 | 不接受该分支 | REJECTED |
| 预算超额、Lease 重复或分配清单冲突 | 违反守恒 | 拒绝 | REJECTED |

## 11. 评估计划与进入真实硬件评估的门槛

### E3 设计冻结验收

- [x] 根预算与分支额度的数学关系明确；
- [x] 在线分配、离线执行、恢复和最终对账流程明确；
- [x] 操作级状态机明确；
- [x] 对崩溃窗口和不确定外部效果给出保守语义；
- [x] Holder 与 Executor 身份分离并分别建立信任关系；
- [x] 明确硬件必须提供的能力，不把模拟器结果当成实机保证；
- [x] 明确不提供即时离线撤销、剩余额度离线回收和 ZK 隐私保证。

### E4 实机可行性评估（尚未开始）

进入实机评估前，必须先选择具体平台并取得可信技术资料，逐项回答：

1. 能否安全生成和使用不可导出 Executor 密钥？
2. 证明是否能绑定实际运行代码、配置和设备身份？
3. 是否有适合本工作负载的防回滚存储/单调版本机制？
4. 更新计数器和写入预留日志是否具备可恢复原子语义？
5. 断电、进程杀死、快照恢复时状态如何表现？
6. 平台是否允许本地工具调用经过可信执行边界？
7. 设备故障后是否能够安全恢复或只能永久锁定额度？
8. 能否在目标操作系统上稳定获取新鲜设备证明？

实机实验至少需要：正常离线消费、并发消费、断电恢复、旧快照恢复、跨设备复制、密钥替换、工具调用超时和最终对账测试。

**不允许** 在未取得平台证据前宣称某台机器支持本架构所需的完整可信状态能力。

## 12. 当前冻结决定与非目标

### 冻结决定

1. 继续采用“在线预分配 + 单 Lease 单设备可信状态 + 离线执行 + 最终对账”的候选架构。
2. 根预算分配依赖单一权威原子状态域；生产多实例部署必须另行证明线性化/共识性质。
3. 离线状态必须通过硬件防回滚和设备绑定保护；当前模拟器只用于协议接口测试。
4. 操作必须先预留预算；结果不确定时保持 `INDETERMINATE` 并占用预算。
5. Tool 幂等能力优先；没有幂等/状态查询时禁止不确定操作自动重试。
6. Lease 在最终对账前不回收剩余额度；v1 不承诺即时离线撤销。
7. Reconciler 的 Executor 公钥和硬件信任根来自独立 Trust Registry，不来自证据包。

### 暂不做

- 不修改 E0/E1/E2 已验收代码；
- 不实现真实 TEE/TPM/安全元件适配；
- 不实现 ZK、匿名凭证或隐藏预算；
- 不增加动态多维成本模型；
- 不把模拟器的通过结果写成真实硬件安全结果；
- 不提交或推送 GitHub。

### 下一阶段

E3 文档冻结后，下一项工作应是 **E4：具体硬件平台可行性评估**，而不是直接写硬件适配代码。先核对目标平台是否具备必要 API 和原子防回滚语义，再决定是否值得购买开发板、使用现有设备或调整研究模型。
