# E1.1 — Trusted executor identity binding

## Finding addressed

E1-04 showed that `BudgetReconciler` previously verified a receipt using the
public key supplied inside the same untrusted `LeaseEvidenceBundle`. An
attacker could create a key pair, sign their own receipts, include the public
key in the bundle, and have that self-selected key accepted as the verification
key.

## Correction

`BudgetReconciler.reconcile` accepts an independently provisioned mapping:

```python
trusted_executor_keys: Mapping[str, bytes]  # lease_id -> raw Ed25519 public key
```

For each manifest lease:

1. Look up the expected executor key from this external mapping.
2. If absent, classify the result as `INCOMPLETE` and do not use the bundle's
   key as a fallback.
3. Require the key carried in the evidence bundle to equal the pinned key.
4. Verify the receipt chain using the pinned key, not a key selected by the
   evidence submitter.

A mismatched bundle key is a hard verification failure (`REJECTED`).

## Principal distinction

The `holder_public_key` in the lease identifies the Agent/holder authorized to
exercise the lease. The executor key identifies the component that signs
execution receipts. These roles may be different (for example, an Agent may
call a trusted execution proxy). Therefore the correction does not force the
executor key to equal `holder_public_key`; it establishes an independent trust
anchor for the executor.

## Trust assumption

The mapping must be provisioned and protected outside the evidence package,
for example by verifier deployment configuration or an independently
administered key registry. This experiment does not implement registry
provisioning, key rotation, revocation, or remote attestation.

## Test interpretation

- Matching pinned key + valid chain: accepted.
- Missing pinned key: incomplete, never accepted.
- Bundle substitutes a self-selected key: rejected.
- Existing receipt signature, chain-order, checkpoint, manifest and budget
  checks remain in place.

The standalone `verify_receipt_chain` helper still verifies signatures under
the key its caller passes; it does not establish trust in that key. The higher-
level reconciler is responsible for checking the key against the independent
trust mapping.
