# E0.3 — Signed execution receipts and hash chain

## Scope

E0.3 adds immutable executor-signed receipts for terminal operations in the
E0.2 in-memory local budget ledger. Each receipt binds:

- the root grant, grant and lease identifiers;
- the ledger operation ID, sequence, cost and terminal state;
- the lease-authorized tool ID and schema hash;
- request, context and (for committed operations) result digests;
- the previous receipt hash and executor key identifier.

Receipts are signed with Ed25519. A domain-separated SHA-256 hash of the full
signed envelope links each receipt to its predecessor.

## Terminal-state semantics

- `committed`: the caller asserts the operation completed; `result_hash` is required.
- `aborted`: the caller asserts no external effect occurred; `result_hash` must be absent.
- `indeterminate`: the external outcome is unknown; `result_hash` must be absent and
  E0.2 continues to count the reserved budget as occupied.
- `reserved`: not terminal, so a receipt cannot yet be appended.

The API does not execute the tool. The caller is responsible for only committing
and appending a `committed` receipt after the external tool result is known.

## Verification

`verify_receipt_chain(...)` verifies:

1. the issuer signature on the lease;
2. the executor signature on every receipt;
3. the chain index and previous-hash links;
4. consistent root/grant/lease/tool/schema binding;
5. unique operation IDs within the supplied chain.

When passed `ledger=...`, verification also requires exact coverage of all
terminal operations in that ledger and checks each receipt's operation sequence,
cost and status against the ledger.

## Important limitations

- The receipt is an executor-signed assertion, not a TEE quote, remote attestation,
  proof of database authenticity, or independent proof of real-world execution.
- The receipt chain is in-memory and process-local; it is not durable or immutable.
- A valid prefix of a hash chain remains valid. Without a trusted final hash,
  independent checkpoint, or trusted ledger view, a verifier cannot detect that
  the tail was removed.
- Ledger completeness checking only helps when the supplied ledger snapshot is
  itself trusted and complete. If an attacker can delete both local ledger state
  and receipts, E0.3 cannot prove the missing operation existed.
- No anti-rollback, cross-process coordination or multi-device global uniqueness
  is provided.

## Reproduction

Run `run_tests.ps1` from the repository root. The full suite includes E0.1,
E0.2 and E0.3 tests.
